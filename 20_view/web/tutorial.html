从零开始，把控制台跑起来

Start from zero

这份教程假设你从没装过。按顺序做，每一步都有验收方式；全程不需要联网，不需要 pip，也不需要 Node.js。

This assumes a fresh machine. Follow the steps in order; each has a way to verify. No internet, no pip, no Node.js.

00它是什么What it is

控制台是一个本地网页：电脑上跑一个小服务，浏览器打开 127.0.0.1:端口 就能看项目状态。它不是云服务，断网也能用；除了首次向导写配置、建任务，它不修改你的项目。

It is a local web page: a small service runs on your machine and the browser shows project status. It is not a cloud service and works offline. Except for the wizard writing config or creating a task, it does not modify your project.

合并优先级固定：core（不可覆盖） > default > user。用户层与内核层同编号时会被拒绝并在页面顶部报告。改完刷新即可，不用重启。

Merge order: core (not overridable) > default > user. A user clause colliding with a core id is rejected and reported. Refresh after editing.

05b三端差异 · 功能与规则怎么开Editions · turning features and rules on

三端是同一份代码，差异只在 web_config.json：capabilities 决定开哪些面板，rules 决定挂哪层规则。personal 5 页、community 3 页、minimal 1 页。

All three editions share one codebase. Only web_config.json differs: capabilities picks panels, rules picks layers. Personal 5 pages, Community 3, Minimal 1.

打开一个功能

Turn a feature on

把能力 id 加进 capabilities 数组，重启 serve.py。例如加 "clients" 就出现接入名册；不加就永远不采数、不显示。

Add a capability id to capabilities and restart serve.py. Without it the panel never loads or shows.

加一条规则

Add a rule

默认层直接往 10_rac/zhunze/（极简端是 10_rac/rules/）放条款 JSON；不想动真身就用规则包：00_meta/rules_library/packs/ 一个 JSON 一个包，"enabled": true 才生效。

Drop a clause JSON into 10_rac/zhunze/ (10_rac/rules/ for Minimal), or use a pack under 00_meta/rules_library/packs/; a pack works only when "enabled": true.

放一个功能包

Drop a feature pack

往 00_meta/feature_packs/ 放一个 JSON，写 capabilities 与 applies_to，"enabled": true 重启即加载；改回 false 面板立刻消失，数据不动。现成两个包：f01_jieru（接入名册）、f02_lishi（日志日历）。

Place a JSON in 00_meta/feature_packs/ with capabilities and applies_to; set "enabled": true and restart. Two ready packs: f01_jieru, f02_lishi.

日志是四层：当天 → 时间 → 项目 → 客户端。四层缺一层，日志就不完整。
Logs render in four layers: day → time → project → client.

05c怎么从零加一个功能Adding a feature from scratch

加功能不是只改页面。要按「能力位 → 后端 → 前端 → 包 → 自证」五步走，少一步就会出现「开关打开却空白」。

A feature is not just a page change. Follow five steps: capability entry, backend, frontend, packs, verification.

第一步：加能力位

Step one: add a capability entry

在 20_view/web/modules.json 的 modules 数组里加一条，字段照现有条目抄齐：id、name、name_en、version、core、min_core、kind、status、group、source、permission、write、credential、evidence、review_by、desc。这张表是各发行版共用定义，须与上游字节一致；本版要不要开，不在这里写，写到本版 web_config.json 的 capabilities。字段名里没有 applies_to——那是包用的，不是能力位用的。

Add an object to modules in 20_view/web/modules.json with the same fields as existing entries: id, name, name_en, version, core, min_core, kind, status, group, source, permission, write, credential, evidence, review_by, desc. This table is shared across releases and must match upstream byte-for-byte. Whether an edition enables it belongs in that edition’s web_config.json under capabilities. applies_to is for packs, not capability entries.

第二步：接后端

Step two: wire the backend

只读数据先加进 snapshot，在 xtgl_core.py 的 /api/overview 返回里多一个字段；需要独立查询就加一条 /api/ 路由。读用 GET，写用 POST，两者都要过同源校验与 permission 权限位；路由里不许写死本机绝对路径，路径一律从配置解析。返回结构固定为状态码与数据两段，出错给可读原因，不要吞掉。

Add read-only data to the snapshot returned by /api/overview in xtgl_core.py, or add a dedicated /api/ route. Use GET for reads and POST for writes; both pass origin checks and the permission flag. Never hard-code absolute paths; resolve them from config. Return a status plus data, and surface readable errors instead of swallowing them.

第三步：挂前端

Step three: attach the frontend

卡片编号以 s- 开头，写进 index.html 的 CAP_MAP，映射到第一步的能力位 id；页签不用手工显隐，applyCaps() 会按 capabilities 自动收起未开启的卡片。词条加在 i18n.js 的中英成对条目里，不许在中文句子里拼英文短语，也不许英文句子夹中文。没有数据时补一句空态文案，不要留白面板。

Give the card an s- prefixed id, register it in CAP_MAP inside index.html, and map it to the capability id from step one. Do not hand-toggle tabs: applyCaps() hides cards whose capability is off. Add paired Chinese and English strings in i18n.js; never mix languages inside one sentence. Provide an empty-state message when no data exists.

第四步：加规则包与功能包

Step four: add rule and feature packs

规则包放 00_meta/rules_library/packs/，功能包放 00_meta/feature_packs/；一个文件一个包，id 必须与文件名一致。enabled 默认 false，改成 true 才生效。applies_to 只填本发行版名（community 或 minimal）；depends_on 只能引用 modules.json 里已有的能力 id。加载顺序固定：先读能力定义，再按各端 capabilities 开关，最后叠加 enabled 的包；包不能改真身条款，也不能预置天数、份数这类数值。

Put rule packs in 00_meta/rules_library/packs/ and feature packs in 00_meta/feature_packs/. One file per pack; the id must match the filename. enabled defaults to false. applies_to accepts only release names (community or minimal). depends_on may reference only capability ids already defined in modules.json. Load order is fixed: capability definitions, then each edition’s capabilities, then enabled packs. Packs must not edit core clauses or preset numeric values.

第五步：加完怎么自证

Step five: prove it works

在本端入口脚本上跑一次严格检查：check --strict（不带 --out；入口脚本名与所在目录见本端 README）。改动核心件后，在本端跑 kernelsync.py --manifest 重算清单。对账点：能力定义与上游字节一致、页面在能力关闭时不出现新面板、打开后能取到真数据、检查结论全绿。任何一项不过，就不要把 enabled 改成 true。

Run the strict check on each edition. After touching core files, run kernelsync.py --manifest per edition. Verify: capability definitions match upstream byte-for-byte, the panel stays hidden when its capability is off, real data loads when on, and every check passes. If any item fails, keep enabled at false.

06任务与留档Tasks & records

每个任务目录至少一份留档，三种文件名都认：benci_gongcheng.txt / renwu_liudang.txt / xiangmu_jilu.txt（或文件名含 liudang）。没有留档会标红。

Each task needs at least one record: benci_gongcheng.txt / renwu_liudang.txt / xiangmu_jilu.txt (or any name with liudang). Missing ones are flagged.

留档三段式：摘要头（日期/执行者/任务/状态/目标）、正文明细、索引尾。执行者写「模型 + 客户端」，不要署用户本人姓名。
A record has three parts: summary header (date/executor/task/status/goal), body, index tail. Write the executor as “model + client”, never the user’s name.

07长期目标与导出Long-term goals & export

目标文件由 web_config.json 的 goals 字段指定，也可以用环境变量 XTGL_GOALS 指向任意路径。仓库里自带 goals.example.txt，复制改一改即可。

The goals file is set by goals in web_config.json, or by the XTGL_GOALS environment variable. A sample ships as goals.example.txt.

每个目标用 [G编号] 开头，字段一行一个「键：值」：目标、阶段、状态、进度、关联项目、关联文件、下一步、证据、复核。右上「导出 Markdown」只导索引，不复制项目文件。

Each goal starts with [Gx] then key/value lines: goal, stage, status, progress, projects, files, next step, evidence, review date. “Export Markdown” exports the index only.

08人工判定Manual checks

有些判断机器算不了（例如「已人工复核」「已知悉未闭环项」）。页面提供人工勾选，勾选结果写入 manual.json，只做记录，不改变机器判据——机器健康仍由闸门和探针决定。

Some judgments cannot be computed (e.g. “manually reviewed”, “acknowledged open items”). Tick them on the page; they are stored in manual.json and do not change machine verdicts.

09常见问题FAQ

双击 .bat 一闪就退

The .bat flashes and closes

三种常见原因：Python 不在 PATH、端口被占、默认浏览器起不来。启动器会打印实际解释器和失败原因；先在终端跑 python serve.py 看真实报错。

Usually Python not on PATH, port busy, or the browser failing. The launcher prints the interpreter and the error; run python serve.py in a terminal to see it.

页面显示「读取失败」

“Read failed” on the page

多半是直接双击了 index.html。必须经 serve.py 启动，页面才能调 /api/*。

You probably opened index.html directly. It must be served by serve.py.

浏览器不是 Chrome / 打不开

Browser is not Chrome / won’t open

服务端优先用 Chrome 新窗口打开，找不到才用系统默认。也可以把终端打印的地址粘到任意浏览器。

The server prefers Chrome; otherwise it falls back to the default browser. Paste the printed URL anywhere.

闸门一直转圈

The gate spinner never stops

闸门是真实执行，项目大时要十几秒；首屏不跑闸门，点按钮才跑。

It really executes; large projects take seconds. First paint skips it.

10边界与卸载Boundaries & uninstall

只监听 127.0.0.1，不做鉴权，不要暴露到局域网/公网；写接口只接受本机页面；除向导外不修改项目。停止用 Ctrl+C；卸载直接删目录，没有注册表、没有系统服务。

Binds to 127.0.0.1 only; no auth, never expose it. Write endpoints accept local pages only. Stop with Ctrl+C; uninstall by deleting the folder.
